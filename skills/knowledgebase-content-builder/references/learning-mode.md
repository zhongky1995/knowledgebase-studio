# Learning Mode

Build the learning experience promised by the product posture, not a knowledge-point catalog and not an automatic training workbench.

For each module define the starting state, reader question, target understanding/judgment/operation, smallest prerequisite set, necessary mechanism, likely misconception, boundary, and appropriate evidence of learning. A saved artifact and feedback route are required only for guided or practice-led learning, not for a reader-led manual.

Sequence knowledge units by dependency and conceptual difficulty. A module label or old folder order is not a progression. Each new unit should rely on already introduced terms and add a controlled number of new relationships.

## Reader-led Manual

Use:

`reader question → useful model → necessary mechanism → example or contrast → boundary → optional reflection`

Make the article readable without first choosing a task, creating an artifact, understanding the whole curriculum, or committing to completion. Preserve the last reading position only as a convenience. Put optional practice after the explanation and label it as optional.

## Guided Learning

Use this progression across a module rather than on every page:

`familiar problem → useful model → necessary mechanism → guided application → realistic output → feedback → transfer`

Use examples when abstraction blocks understanding, mechanisms when memorized steps would cause misuse, contrasts when boundaries matter, diagrams when relationships are hard to hold, and practice when the ability needs active use.

Treat a visual as an explanation contract, not page decoration. Prefer a table for repeated exact mappings, a static diagram for stable spatial relationships, and animation only when flow, feedback, accumulation, transformation, focus, or state change carries part of the mechanism. When required by `learning-design.json`, apply `knowledgebase-visual-explainer`, deliver the real embedded asset, and keep an accessible static fallback for animation.

Give each lesson one primary learning result. Define abbreviations before use. Keep the main explanation visible and move secondary depth elsewhere.

When a worked example is necessary, choose the learning job. Judgment/creation examples expose realistic input, first attempt, reasoned judgment, revision, revised output and transfer. Concept explanations may use `mechanism_trace`: situation, participants, intermediate actions, outcome, boundary and changed condition; see `novice-mental-model.md`. A finished answer or list of principles without the relevant process is insufficient.

When practice is part of the promised posture, it should resemble real judgments or outputs and have an answer, rubric, or feedback path. A running case is optional and should not repeat stable setup. A progress definition alone cannot establish mastery: claims need appropriate assessment evidence, not clicks or filled fields.

For operational walkthroughs and interactive inquiry, read the shared learning reviewer's `references/learning-activity-design.md`. Connect a learning action to evidence-dependent feedback, optional hints, revision, and changed transfer material as needed. These are composable teaching moves, not mandatory widgets or a fixed loop on every page. Keep explanations and text alternatives available to readers who skip practice.

Estimate reading time from visible prose, tables, diagrams, decisions, and any promised practice. Treat a character-count estimate as a baseline, not evidence that a novice can complete the page in the advertised time.
